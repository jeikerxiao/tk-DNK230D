# 实验7 RTC实验

> 设置芯片内部实时时钟并从串口每秒打印一次时间，学会给开发板"对上表"。难度：初级

## 1. 例程简介

本例程使用 K230D 芯片内部的 **RTC（Real Time Clock，实时时钟）**：先用代码设置一个初始日期时间（2024 年 9 月 12 日星期四 8:00:00），然后在主循环中每秒打印一次当前时间，你会看到秒、分、时自动进位走动。你将学会 RTC 对象的创建、`datetime()` 的设置与读取，理解"系统时间"从何而来。难度为**初级**，RTC 是日志记录、定时任务、照片水印等应用的时间基础。

## 2. 硬件连接与原理

本实验**不使用任何引脚和外设**，只用到芯片内部资源和串口打印：

| 资源 | 说明 |
| --- | --- |
| RTC | K230D 芯片内部的实时时钟模块，代码对象 `rtc` |
| 串口终端 | `print()` 通过 USB 虚拟串口输出到 CanMV IDE 终端 |

没有按键、LED、屏幕参与，也无需 FPIOA 映射——这是 16 个实验中硬件依赖最少的一个。

### 硬件原理（通俗版）

RTC 是芯片里一块**独立走时的"手表"**：它由低速时钟源驱动，即使 CPU 忙着跑你的程序，RTC 也在后台默默地数着秒、分、时、日。你只需要：

1. **对表**：告诉它"现在是几点"（写入初始时间）；
2. **读表**：随时问它"现在几点"（读出当前时间），它返回的时间 = 初始时间 + 走过的时长。

与用 `time.sleep()` 自己数秒不同，RTC 走时由硬件维护，程序卡一下、循环慢一点都不会让时间"漂移"。

> [!NOTE]
> RTC 的走时依赖供电。开发板断电后 RTC 是否继续走时取决于板上是否有后备电源（如纽扣电池座/超级电容）。若完全断电后时间丢失，重新上电后 RTC 会停走或复位，需要再次"对表"——这也是代码每次运行都先设置时间的原因。

### 新手风险提醒

> [!WARNING]
> - 本实验无接线需求，风险极低；但仍不要在运行中拔插 USB 线，以免 IDE 通信异常。
> - RTC 时间是"软件财产"，掉电可能丢失，重要项目应设计好时间同步机制（如联网对时）。

## 3. 相关前置知识

- **RTC（实时时钟）**：芯片内部独立走时的日历+时钟模块，见上文通俗解释。
- **元组（tuple）**：Python 的一种数据写法 `(a, b, c)`，用小括号把多个值按顺序打包。`datetime()` 用一个 8 元素元组表示时间。
- **时间的 8 元组格式**：`(年, 月, 日, 星期, 时, 分, 秒, 微秒)`。代码注释明确说明：**星期用 0~6 表示星期一~星期日**。2024-09-12 正是星期四，对应 `3`。
- **`time.sleep(1)`**：延时 1 秒（注意单位是秒；`sleep_ms()` 才是毫秒）。控制打印节奏，让终端每秒刷新一行。
- **串口打印**：`print()` 的内容经 USB 线传到电脑，显示在 CanMV IDE 的终端窗口。

## 4. 软件代码逻辑说明

代码极简，流程：**创建 RTC 对象 → 设置初始时间 → 循环打印**。

### 第 1 步：导入模块并创建 RTC 对象

```python
from machine import RTC
import time

rtc = RTC()
```

`RTC()` 直接使用芯片内部的 RTC 外设，无需参数、无需引脚映射。

### 第 2 步：设置日期时间（对表）

```python
# 设置RTC日期和时间。(2024, 9, 12, 3, 8, 0, 0, 0)按顺序分别表示（年，月，日，星期，时，分，秒，微妙），
# 其中星期使用0-6表示星期一到星期日。

rtc.datetime((2024, 9, 12, 3, 8, 0, 0, 0))
```

`datetime()` **传入元组时是"设置时间"**：把 RTC 拨到 2024 年 9 月 12 日、星期四、早上 8 点 0 分 0 秒 0 微秒。

> [!NOTE]
> 注意是"双层括号"：外层是函数调用的括号，内层是元组本身的括号，少写一层会报错。

### 第 3 步：循环读取并打印（读表）

```python
while True:
    print(rtc.datetime()) #打印时间
    time.sleep(1) #延时1秒
```

`datetime()` **不带参数调用时是"读取时间"**，同样返回 8 元组。每读一次打印一行，然后睡 1 秒，于是终端每秒出现一行走动的时间。

### 关键 API 小结

| API | 作用 |
| --- | --- |
| `RTC()` | 创建 RTC 对象 |
| `rtc.datetime((年,月,日,星期,时,分,秒,微秒))` | 设置当前时间 |
| `rtc.datetime()` | 读取当前时间，返回 8 元组 |

### 可调参数

- 初始时间元组 `(2024, 9, 12, 3, 8, 0, 0, 0)`：改成你运行当天的真实日期时间（别忘了核对星期对应的 0~6），这样打印出来的就是"真时间"。
- `time.sleep(1)`：改成 0.5 打印更快，改成 60 则每分钟一行。
- 想让打印更易读，可以拆包格式化：

```python
t = rtc.datetime()
print("%04d-%02d-%02d %02d:%02d:%02d" % (t[0], t[1], t[2], t[4], t[5], t[6]))
```

注意下标：`t[3]` 是星期，时、分、秒分别是 `t[4]`、`t[5]`、`t[6]`。

## 5. 运行效果

- **成功现象**：IDE 串口终端每秒打印一行类似：

  ```text
  (2024, 9, 12, 3, 8, 0, 0, 5749)
  (2024, 9, 12, 3, 8, 0, 1, 6210)
  (2024, 9, 12, 3, 8, 0, 2, 6672)
  ```

  倒数第三个数字（秒）每秒加 1；微秒字段（最后一位）每次读取略有不同，属于正常现象；60 秒后分钟进位，60 分后小时进位。
- **失败现象排查**：
  1. 无打印 → IDE 终端窗口是否打开、程序是否在运行。
  2. 时间不走动 → 检查是否误把 `rtc.datetime()` 写成了带参数形式（那是设置而不是读取）。
  3. 打印的秒数跳变不规律 → `sleep(1)` 加上打印本身耗时约几毫秒，长期运行会与真实时间有微小偏差，属正常。

## 7. 拓展思考

1. **只对表一次**：给程序加判断——读取 RTC 时间，若年份明显不对（如小于 2024）才设置初始时间，否则直接走时。思考这样做在"脱机运行"场景下的意义。
2. **整点报时**：结合[实验2 蜂鸣器实验](../实验2%20蜂鸣器实验/README.md)，检测到 `分==0 且 秒==0` 时用 PWM 让蜂鸣器"滴"一声，制作整点报时器。
3. **定时开关灯**：结合[实验1 跑马灯实验](../实验1%20跑马灯实验/README.md)，设定"8:00:10 点亮红灯、8:00:30 熄灭"的日程表，把 RTC 从"读时间"升级为"用时间做决策"。

## 8. 常见问题

**Q1：元组里第 4 个数 `3` 是"3 号"吗？**
A：不是！顺序是 `(年, 月, 日, 星期, 时, 分, 秒, 微秒)`，第 4 位是**星期**。`3` 表示星期四（0=星期一 … 6=星期日）。2024 年 9 月 12 日恰好是星期四，所以代码这样写。日期是第 3 位的 `12`。

**Q2：为什么打印出来的微秒数总是"不整"，比如 5749、6210？**
A：微秒是 RTC 内部高精度计数的低位，`print` 那一刻读到什么就是什么，加上 `sleep(1)` 和打印本身的执行耗时，每行的微秒值都会不同。这不影响秒级以上的精度。

**Q3：断电重启后时间还是对的吗？**
A：不一定。RTC 掉电后可能停止走时，且本代码每次运行都会强制重新设置为 2024-09-12 08:00:00。想要断电后保持时间，需要板上有后备供电，并且程序改成"只在时间无效时对表"（见拓展思考 1）。

**Q4：`time.sleep(1)` 和 `time.sleep_ms(1000)` 有区别吗？**
A：效果一样，都是延时 1 秒，只是单位不同：`sleep()` 以秒为单位（可写小数），`sleep_ms()` 以毫秒为单位。混用单位是新手常见错误，比如 `time.sleep(1000)` 会睡 1000 秒！

**Q5：RTC 和 `time.ticks_ms()` 这类计时有什么区别？**
A：`ticks_ms()` 只是"从上电起过了多少毫秒"的计数，用于测量时间间隔；RTC 维护的是"日历+钟表"绝对时间，能回答"现在是几月几号几点"。做间隔测量用 ticks，做日历时钟用 RTC。
